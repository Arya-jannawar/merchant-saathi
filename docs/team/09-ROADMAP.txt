FUTURE (TALK, DON'T BUILD)
  - Scale path for millions of merchants: managed PostgreSQL + durable jobs
    behind the existing repository seam (pure domain functions make this a
    contained change); per-merchant fact packs already make chat grounding
    per-tenant.
  - Real messaging integrations only with merchant-authorized consent and
    provider APIs; the consent register is already the right shape.
  - Demand forecasting ML: only after a real pilot produces data worth
    learning from. The current "opportunity" is an explainable rule on
    purpose.
  - Deeper domain coverage: more domains = copy the fixture, keep the
    numbers, add to the registry (see file 04 checklist).

PILOT PLAN (business validation, from the pitch deck)
  - Target: 3-5 Pune merchants across 2-3 domains.
  - Question: can they prepare a sound offer faster, manage stock with fewer
    surprises, and would they pay monthly? Subscription covers recurring
    sales reviews, offer preparation with evidence checks, campaign
    reporting, and operations intelligence.
  - Measure: time-to-prepare an offer (with vs without), pricing errors,
    stockouts per week, comprehension of the evidence. Small, exploratory
    sample - label it as such.
  - Costs to track: model usage, onboarding, support.

THE ONE RULE FOR EVERYTHING ABOVE
  If adding a feature would make any label less honest or any test red,
  it goes BELOW fixing the core. A small, complete, truthful loop beats a
  big, wobbly one - in judging and in production.
